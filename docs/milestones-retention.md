## 1. What is stored

The backend handles milestones in two distinct contexts, each with its own
persistence model:

| Context | Where stored | Retention model |
|---------|-------------|-----------------|
| **Milestones embedded in contracts** | SQLite `contracts` table (as JSON inside the contract record) | Inherits contract retention — indefinite, no automated purge |
| **Standalone milestones** (soft-delete / restore / purge API) | In-memory `Map` (`milestoneStore`) | Configurable soft-delete window, then hard-purge |

Both contexts share the same `MilestoneRecord` shape and the same
soft-delete utilities from `src/utils/softDelete.ts`.

---

## 2. Storage location

### 2a. Contract-embedded milestones

Milestone arrays are stored inside contract rows in the SQLite database
file (default `talenttrust.db`, override with `DB_PATH`). They are part
of the contract's JSON payload column — not a separate table.

**Source:** `src/repositories/contractRepository.ts`,
`src/modules/contracts/dto/contract.dto.ts`

### 2b. Standalone milestones

The standalone `MilestonesService` uses a module-level in-memory `Map`:

```typescript
// src/services/milestones.service.ts (line 62)
/** In-memory store for milestones (demo persistence; production would use SQLite). */
const milestoneStore = new Map<string, MilestoneRecord>();
```

This store is **ephemeral** — it is cleared on every process restart and is
not persisted to SQLite or any external database. It is intended for local
development and testing. Production use requires a durable storage backend.

## 3. Milestone record shape

**Source:** `src/services/milestones.service.ts` → `MilestoneRecord`

```typescript
interface MilestoneRecord {
  id: string;           // UUID generated by crypto.randomUUID()
  contractId: string;   // Parent contract identifier
  title: string;        // User-supplied title (1–100 chars)
  description: string;  // User-supplied description (1–500 chars; defaults to '')
  amount: number;       // Payment amount (positive; in stroops for blockchain context)
  deadline?: string;    // Optional ISO 8601 datetime string
  completed: boolean;   // Completion flag; defaults to false
  createdAt: Date;      // Set on creation; never mutated
  updatedAt: Date;      // Updated on every mutation
  deletedAt?: Date | null; // null/undefined = active; Date = soft-deleted
}
```

### Contract-embedded milestone fields

When milestones are part of a contract (created via `POST /api/v1/contracts`
or `PATCH /api/v1/contracts/:id`), the stored shape is defined in
`src/modules/contracts/dto/contract.dto.ts`:

| Field | Type | Required | Constraints |
|-------|------|----------|-------------|
| `title` | `string` | Yes | 1–100 characters |
| `description` | `string` | No (defaults to `''`) | 1–500 characters |
| `amount` | `number` | Yes | Positive (`> 0`) |
| `deadline` | `string` | No | Valid ISO 8601 datetime |
| `completed` | `boolean` | No | Defaults to `false` |

**Policy bounds** (`src/contracts/bounds.ts`):

| Constant | Value | Enforcement |
|----------|-------|-------------|
| `MAX_MILESTONES_PER_CONTRACT` | `20` | Validated at create/update; returns `422 contract_bounds_error` |
| `MAX_CONTRACT_AMOUNT_STROOPS` | `100,000,000,000,000` | Sum of milestone amounts must not exceed this cap |

Sum of milestone `amount` values must also not exceed the parent
contract's `budget` field (`src/services/contracts.service.ts`).

## 4. Retention windows

### 4a. Contract-embedded milestones

Contract-embedded milestones have **no automated retention window or expiry**.
They are kept for as long as their parent contract exists in the `contracts`
table. No scheduled job, cron task, or `src/retention/purge.ts` handler
targets contract rows or their embedded milestone arrays.

See [`docs/contracts-retention.md`](contracts-retention.md) for the full
contract retention policy.

### 4b. Standalone milestones (in-memory store)

Standalone milestones implement a **soft-delete retention window** before
hard purge. The window is configurable and defaults to **30 days**.

| Variable | Default | Description |
|----------|---------|-------------|
| `MILESTONES_SOFT_DELETE_RETENTION_DAYS` | `30` | Days a soft-deleted milestone can be restored before purge |

**Source:** `src/services/milestones.service.ts` →
`MILESTONES_SOFT_DELETE_RETENTION_DAYS_ENV`,
`src/utils/softDelete.ts` → `DEFAULT_SOFT_DELETE_RETENTION_DAYS`

Timeline for a standalone milestone:

```
Created (deletedAt = null)
    │
    │  Active: visible in default reads, restoreable N/A
    │
SOFT-DELETE called  ──→  deletedAt = NOW
    │
    │  Within window (0–30 days):
    │    - Hidden from default reads
    │    - Restorable via restore()
    │
    │  Past window (> 30 days):
    │    - Hidden from default reads
    │    - Restore rejected with 410 SoftDeleteRetentionError
    │
PURGE (purgeExpired) ──→  Record permanently removed from milestoneStore
```

Because the store is in-memory, the effective retention also resets on
every process restart — there is no durable `deletedAt` persisted to disk.

## 5. Soft-delete lifecycle

All soft-delete logic is implemented in `src/utils/softDelete.ts` and
consumed by `MilestonesService` (`src/services/milestones.service.ts`).

### 5a. Soft-delete

`MilestonesService.softDelete(contractId, milestoneId, now?)`:

- Sets `deletedAt = now` on the record.
- Record is excluded from `listByContract()` and `getById()` unless
  `{ includeDeleted: true }` is passed.
- Returns `409 MilestoneConflictError` if already soft-deleted.

### 5b. Restore

`MilestonesService.restore(contractId, milestoneId, now?)`:

- Clears `deletedAt = null`.
- Only allowed while `deletedAt` is within the retention window
  (checked via `isWithinRetentionWindow` from `softDelete.ts`).
- Returns `410 SoftDeleteRetentionError` if the window has elapsed.
- Returns `409 MilestoneConflictError` if the milestone is not soft-deleted.

### 5c. Hard-purge

`MilestonesService.purgeExpired(now?)`:

- Iterates all records in `milestoneStore`.
- Calls `isPastRetentionWindow(record.deletedAt, retentionDays, now)`.
- Records that are soft-deleted **and** past the window are permanently
  removed via `milestoneStore.delete(id)`.
- Returns the count of purged records.

This method must be called explicitly — there is **no scheduled background
job** that calls it automatically in the current implementation.

## 6. Purge behavior

### 6a. Standalone milestones

| Trigger | How | Result |
|---------|-----|--------|
| `purgeExpired()` called | Explicit call — no automation | Permanently deletes soft-deleted records past the retention window |
| Process restart | In-memory store cleared | All records (active and soft-deleted) lost |

No records are written to disk, so there is no archival step before purge.

### 6b. Contract-embedded milestones

Contract-embedded milestones are **not purged by any automated mechanism**.
They can only be removed by:

- Explicitly patching the parent contract to remove the milestones array
  (`PATCH /api/v1/contracts/:id` with an updated milestones list).
- Hard-deleting the parent contract (`deleteContract()` in
  `src/services/contracts.service.ts`), which cascades via SQL.

### 6c. Relation to the retention engine (`src/retention/`)

The `src/retention/` module defines `DataEntityType.CONTRACT` but does **not**
define a `DataEntityType` for milestones, and no `RetentionPolicy` targeting
milestones is registered or applied in the current production code.
Milestone records are entirely outside the automated retention/archival
pipeline (`src/retention/policies.ts`, `src/retention/archival.ts`,
`src/retention/purge.ts`).

## 7. Contract-embedded milestones vs. standalone milestones

The two contexts behave differently in every dimension:

| Dimension | Contract-embedded | Standalone (MilestonesService) |
|-----------|-------------------|-------------------------------|
| **Storage** | SQLite `contracts` table (durable) | In-memory `Map` (ephemeral) |
| **Access** | Via contracts API (`/api/v1/contracts`) | Via milestones controller (`/api/v1/contracts/:id/milestones`) |
| **Soft-delete** | Not implemented | Implemented (`softDelete` / `restore` / `purgeExpired`) |
| **Retention window** | None — indefinite | 30 days (configurable) |
| **Automated purge** | None | Manual call to `purgeExpired()` required |
| **Restart durability** | Persisted | Lost on restart |
| **Feature flag** | `MILESTONES_ENABLED` strips at ingestion | Not affected |
| **Validation** | `MAX_MILESTONES_PER_CONTRACT`, `MAX_CONTRACT_AMOUNT_STROOPS`, budget cap | `validateBounds()` / `validateMilestonesAgainstBudget()` |

## 8. PII handling

### Fields assessed

| Field | PII risk | Notes |
|-------|----------|-------|
| `id` | None | UUID generated by `crypto.randomUUID()` — no personal data |
| `contractId` | Low | Internal UUID; links to a contract but not directly to a person |
| `title` | Moderate | **Free-text user input.** Could contain names, project names, or other personal details if the user includes them. No server-side sanitisation beyond length validation. |
| `description` | Moderate | **Free-text user input.** Same risk as `title`. |
| `amount` | None | Financial amount; not linked to identity |
| `deadline` | None | A date; no personal information |
| `completed` | None | Boolean flag |
| `createdAt` / `updatedAt` | None | Operational timestamps |
| `deletedAt` | None | Retention timestamp |

### Current protections

- **No PII-specific redaction** is applied to milestone fields before persistence. The `src/audit/redact.ts` `maskEmail` helper and the `src/utils/redact.ts` object-redaction utilities are **not** applied to milestone payloads.
- **Log redaction**: The structured logger (`src/logger.ts`) redacts keys matching `secret`, `token`, `password`, `authorization`, `key`, `signature`, `cookie`, and `nonce` before emitting log lines. Milestone `title` and `description` do not match these patterns and are **not** redacted from debug logs.
- **HTTP log redaction**: The request logger (`src/middleware/requestLogger.ts`) redacts credential-bearing HTTP headers but does not redact request body content. Milestone payloads in request bodies may appear in debug-level logs.

### Recommendations

1. If milestones move to durable SQLite storage, apply column-level length
   and encoding constraints on `title` and `description`.
2. Consider running `title` and `description` through the existing
   `redactObject` / `sanitize` middleware before persisting, or at minimum
   before emitting debug logs.
3. If GDPR or CCPA data-subject deletion requests are required, implement
   a milestone purge path keyed by `contractId` (which maps to a user).

## 9. Configuration reference

| Variable | Default | Source | Effect |
|----------|---------|--------|--------|
| `MILESTONES_SOFT_DELETE_RETENTION_DAYS` | `30` | `src/services/milestones.service.ts` → `MILESTONES_SOFT_DELETE_RETENTION_DAYS_ENV` | Retention window (days) for soft-deleted standalone milestones before they become eligible for hard purge |
| `MILESTONES_ENABLED` | `true` | `src/config/features.ts` | When `false`, any `milestones` field in a contract create/update request is silently stripped; standalone milestones API is unaffected |
| `DB_PATH` | `talenttrust.db` | `src/db/database.ts` | Path to the SQLite file that holds contract-embedded milestones; use `:memory:` in tests |

The retention window is parsed defensively — invalid values (non-numeric,
zero, negative) fall back to the 30-day default via `parseRetentionDays()`
in `src/utils/softDelete.ts`.
